# 受信

Redmine AWS SES が、SES の受け取ったメールを取り込むしくみです。アドレス、プロジェクトの決め方、なりすましとスパムの確認、Redmine の `MailHandler` に渡すオプションを書きます。SES は、メッセージをメールのバケット (`inbound/<メッセージ ID>`) に置き、取り込みを起動します。ドメイン、受信ルール、バケットは [Serverless の mail.md](https://redmine-kit.github.io/serverless/ja/mail.html#receiving) にあります。

2026-11-09 に Redmine 7.0.3 のソースで、2026-11-12 に SES の受信通知の資料 ([Contents of notifications for Amazon SES email receiving](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-notifications-contents.html)、[Deliver to S3 bucket action](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-action-s3.html)) で確認しました。

<a id="addresses-per-project"></a>

## プロジェクト別のアドレス

| アドレス | 使い方 |
| --- | --- |
| `<プロジェクトの識別子>@<ドメイン>` | プロジェクトのアドレス。ここに届いたメールは、そのプロジェクトのチケットになる。プロジェクトの通知を、ここから送ることもできる ([sending.md](sending.md#senders-per-project)) |
| `noreply@<ドメイン>` (デフォルトアドレス) | プロジェクトに属さないメールの送信元 (下の「デフォルトアドレス」) |

`<ドメイン>` は Redmine のドメインで、送信元メールアドレス (`Setting.mail_from`) のドメインです。

- **識別子とアドレス:** プロジェクトのアドレスは、識別子を `@` の前にしたものだけです。Redmine のプロジェクトの識別子は、英小文字、数字、`-`、`_` でできているので、そのまま使えます。識別子が 64 文字 (`@` の前の上限) より長いプロジェクトは、メールを受け取れず、通知の送信元も送信元メールアドレスのままです。
- **ロールアドレス:** プロジェクトは、ロールアドレス (`postmaster`、`abuse`、`hostmaster`、`webmaster`、`mailer-daemon`、`root`、`admin`、`administrator`、`noreply`、`no-reply`、`security`、`support`。RFC 2142 と一般的なもの) も使えます。たとえば、外部のメールボックスから意図して転送する `support@` です。ほかのメールサーバーが報告を送るものもあり (`postmaster@` へのバウンス、`abuse@` への不正利用の報告)、それもチケットになるので、「メール受信」のタブは、ロールアドレスでメールを受け取るプロジェクトごとに警告を出します。
- **デフォルトアドレス:** 識別子がデフォルトアドレスの `@` の前と同じプロジェクトは、そのアドレスでメールを受け取りません。デフォルトアドレスが受け取ります。タブは、これにも警告を出します。
- **送信元メールアドレス:** 通知への返信は、送信元メールアドレス (`Setting.mail_from`) に届きます。それがデフォルトアドレスと異なるときは、デフォルトアドレスと同じくメールを受け取り (同じプロジェクト、または取得しない)、タブは警告を出します。返信が「未取得 (プロジェクトなし)」にならないようにするためです。
- **受け取るか:** プロジェクトごとに、メールを受け取るかを選びます (「メール受信」。デフォルトはオフ)。受け取らないプロジェクトへのメールは、取り込まずに記録します。
- **プロジェクトの設定:** プロジェクトの設定の「メール」のタブで、受け取るかとデフォルト値を決めます ([admin.md](admin.md#project-email-settings))。設定は、プラグインのテーブル (`aws_ses_project_mail_settings`) に入ります。

<a id="without-addresses-per-project"></a>

## プロジェクト別のアドレスを使わないとき

プロジェクトごとのアドレスが無効 (デフォルト) なら、Redmine の標準と同じに受け取ります。

- **受け取るアドレス:** デフォルトアドレスだけです。
- **プロジェクトの決め方:** Redmine のサブアドレス (`noreply+<識別子>@<ドメイン>`) です。プラグインは、サブアドレスを `To` と `Cc` のヘッダーではなく、エンベロープの宛先から読むので、Bcc でも決まります。サブアドレスのないメールは、「メール受信」のタブの「受信メール」のとおり、デフォルトのプロジェクトで取得するか、取得しません。
- **送信元:** すべての通知を、デフォルトアドレスから送ります。

<a id="address-for-the-whole-redmine"></a>

## デフォルトアドレス

プロジェクトに属さないメールは、送信元メールアドレス (`Setting.mail_from`)、つまりデフォルトアドレスから送ります。

| デフォルトアドレスから送るメール | Redmine のメーラーメソッド |
| --- | --- |
| パスワードの再設定 | `lost_password` |
| アカウント登録の確認、有効化の依頼、有効化の通知 | `register`<br>`account_activation_request`<br>`account_activated` |
| アカウント情報 (システム管理者が作ったアカウント) | `account_information` |
| 期日のリマインダー (複数のプロジェクトのチケットをまとめる) | `reminder` |
| セキュリティ通知、設定変更の通知 | `security_notification`<br>`settings_updated` |
| テストメール | `test_email` |

上のメソッドは、Redmine 7.0.3 のメーラーのうち、プロジェクトのヘッダー (`X-Redmine-Project`) を付けないものです (`app/models/mailer.rb`)。

- **`@` の前:** 「メール受信」のタブの「受信設定」の「デフォルトアドレス」で決めます。デフォルトは `noreply` で、「受信メール」のデフォルトの「取得しない」に合わせています。取得に切り替えるときに、`@` の前を決めます (例: `redmine`)。受信設定を保存済みの環境では、保存した値のままです。同じ識別子のプロジェクトは、このアドレスでメールを受け取れません。
- **そこに届いたメール:** 「受信メール」で、「取得しない」(デフォルト) か「デフォルトのプロジェクトで取得」を選びます。パスワードの再設定などへの返信は、ふつう取得する必要はありません。

<a id="importing"></a>

## 取り込み

rake タスク `redmine_aws_ses:receive_mail` が、メッセージを 1 通取り込みます。

1. メッセージの記録をロックします (メッセージごとに 1 つずつ。下記)。取り込み済みで、そのチケットや注記が残っていれば、終わります。
2. メールのバケットでメッセージを探します (`inbound/`。再取得なら `processed/` に `HeadObject`)。40 MB より大きいメッセージは取り込みません。SES が保存するのは、ヘッダーを含めて 40 MB までです ([Deliver to S3 bucket action](https://docs.aws.amazon.com/ses/latest/dg/receiving-email-action-s3.html))。記録の差出人と件名のために最初の 64 KiB だけを読み、「未取得 (サイズ超過)」として記録します。
3. 全文を取ります。
4. SES のイベントと Redmine だけから決めます。判定 (下の「なりすましとスパム」)、イベントの宛先からのプロジェクト (下記)、誰のメッセージか (下の「転送メール」) です。
5. Redmine の `MailHandler.safe_receive` に、全文 (またはメンバーが転送した元のメール) とオプションを渡します。Redmine の `rake redmine:email:read` と同じ処理です。
6. 成功したら、記録を保存したあとで、メッセージを `processed/` に移します (`CopyObject` のあと `DeleteObject`)。実行ごとに記録を残します ([admin.md](admin.md#receiving-email))。

**メッセージごとに 1 つずつ:** SES は取り込みを非同期で呼び出し、もう一度呼び出すことがあります。「再取得」でも実行が始まるので、同じメッセージの実行が重なることがあります。実行は、トランザクションの中でメッセージの記録をロックし (`SELECT … FOR UPDATE`)、チケットも同じトランザクションで作ります。最初の実行が 2 つ重なると、メッセージ ID の一意のインデックスで、2 つ目が失敗します。2 つ目は作ったチケットをロールバックし、1 つ目の記録でもう一度動いて、そこで終わります。シリアライズの失敗とデッドロックも、1 回だけやり直します。1 通のメールから 2 つのチケットはできません。

**入れ子のトランザクションなし:** 取り込みは、自分のトランザクションの中で別のトランザクションを開かないので、セーブポイントのないデータベースでも動きます。Redmine がメッセージを受け付けないときは、トランザクション全体をロールバックし、新しいトランザクションでもう一度動きます。受け付けられなかったメンバーの転送は、メンバー自身のメッセージとして、受け付けられなかったメッセージは「取得エラー」として記録します。

タスクは、SES のイベントの値を、変数で受け取ります。

| 変数 | SES のイベントの値 |
| --- | --- |
| `MESSAGE_ID` | `mail.messageId` (メールのバケットのキー) |
| `SES_RECIPIENTS` | `receipt.recipients` (エンベロープの宛先。カンマ区切り) |
| `SES_MAIL_FROM` | `mail.source` (エンベロープの MAIL FROM のアドレス)。登録した転送元のため (下の「転送メール」)。省略できる。省略すると、どのメッセージも転送元のものになりません |
| `SES_SPAM_VERDICT`<br>`SES_VIRUS_VERDICT`<br>`SES_DMARC_VERDICT`<br>`SES_SPF_VERDICT`<br>`SES_DKIM_VERDICT` | `receipt.spamVerdict.status` など |
| `SES_DMARC_POLICY` | `receipt.dmarcPolicy` |

Lambda では、SES の受信ルールがタスクの関数を呼び出し、そのハンドラーがこれらを設定します ([Serverless の tasks.md](https://redmine-kit.github.io/serverless/ja/tasks.html#kinds-of-events))。再取得では `MESSAGE_ID` だけを渡し、最初の実行で記録したものを使います。

**プロジェクトの決め方:**

- **宛先は SES のイベントから取る:** `To` と `Cc` のヘッダーではなく、エンベロープの宛先 (SMTP の `RCPT TO`) を使うので、Bcc で届いたメールも決まります。再取得のために、取り込みの記録に残します。
- **当てはめ方:** 宛先のうち Redmine のドメインのアドレスを順に見て、メールを受け取るプロジェクトの識別子に当てはまる最初のものにします。当てはまるものがなければ、取り込まずに記録します。
- **Redmine に渡す:** プロジェクトの識別子とデフォルト値を、`MailHandler` のオプション (`issue[:project]` など) で渡します。Redmine の決め方では本文の `Project:` のキーワードが勝つので、`allow_override` を空にし、キーワードでプロジェクトを変えられないようにします。
- **返信:** Redmine は、通知メールへの返信を、`In-Reply-To` と `References` のヘッダーから、元のチケットの注記にします (`MailHandler#dispatch`)。返信をどのアドレスに送っても、元のチケットに付きます。

| オプション | 値 | 意味 |
| --- | --- | --- |
| `unknown_user` | プロジェクトの設定 (デフォルトは `ignore`) | Redmine に登録していないアドレスからのメールの扱い |
| `no_permission_check` | `0` | 送信者の権限を確認する |
| `allow_override` | 空 | 本文のキーワードで属性を変えない |
| `issue[:project]` | 宛先から決めたプロジェクト | 上記 |
| `issue[:tracker]` などのデフォルト値 | プロジェクトのデフォルト値 (名前で渡す) | 作るチケットの値 |

- **自動返信:** `Auto-Submitted` (`auto-replied`、`auto-generated`) か `X-Autoreply: yes` のあるメール (`MailHandler.ignored_emails_headers`) は、取り込まずに、自動返信として記録します。通知と取り込みが繰り返されないようにするためです。
- **Redmine が取り込まないとき:** `MailHandler` が受け付けないメール (たとえば、`ignore` のときの未登録の送信者や、権限のない送信者) は、取り込まなかったものとして記録し、`inbound/` に残します。理由は Redmine のログにあります。
- **添付ファイル:** 添付ファイルは Redmine の添付ファイルとして保存します ([Redmine AWS S3](https://redmine-kit.github.io/redmine_aws_s3/ja/) があれば S3 に置きます)。

<a id="spoofing-and-spam"></a>

## なりすましとスパム

Redmine は、メールの差出人 (`From`) のアドレスで、どのユーザーからのメールかを決めます。差出人を偽ったメールを取り込むと、そのユーザーとしてチケットが作られます。そこで、取り込みは、SES のイベントの判定を確認します。

| イベントの判定 (`receipt`) | `PASS` でないとき | 設定 |
| --- | --- | --- |
| `virusVerdict.status` | いつも取り込まない。添付ファイルが全員に配られるため | — |
| `spamVerdict.status` | 取り込まない | 「スパムも取得」(`import_spam`。デフォルトはオフ) |
| `dmarcVerdict.status` | 取り込まない | 「DMARC に失敗したメールも取得」(`import_without_dmarc_pass`。デフォルトはオフ) |

値は `PASS`、`FAIL`、`GRAY`、`PROCESSING_FAILED` のどれかです。判定がないときは、`PASS` でないものとして扱います。`spfVerdict` は、登録した転送元のときだけ判断に使います (下の「転送メール」)。`dkimVerdict`、`dmarcPolicy` も記録しますが、取り込むかどうかの判断には使いません。判定は、取り込んだかどうかにかかわらず記録します。

- **デフォルトで DMARC を求める理由:** DMARC に合格していれば、差出人のドメインが SPF か DKIM で確認されています。Microsoft 365 や Gmail から送ったメールは、ふつうは合格します。設定をオンにすると、誰でも、登録済みのユーザーの名前でメールを送れてしまいます。
- **SES のイベントから取り、ヘッダーからは取らない:** 判定と宛先はイベントから取り、メッセージのヘッダー (`X-SES-*`、`Authentication-Results`) からは取りません。送信者が同じ名前のヘッダーを付けられるからです。
- **判定がないとき:** 判定のないメッセージ (イベントからも、前の記録からも得られないもの) は取り込みません (`no_verdict`)。
- **再取得:** 取り込みの記録が判定と宛先を持ち、再取得ではそれを使います。設定は、そのときのものを使います。

<a id="forwarded-email"></a>

## 転送メール

転送されたメールがプロジェクトに届く経路は 2 つあります。外部のメールボックスが受け取ったメールをすべてプロジェクトのアドレスに転送するもの (自動転送) と、メンバーが顧客のメールをメールソフトから転送するもの (メンバーによる転送) です。判断はコードの 1 か所 (`RedmineAws::SES::Admission`) で、SES のイベントと Redmine だけから行います。メッセージのヘッダーは、送信者が偽れるので、判断に使いません。

<a id="automatic-forwarding"></a>

### 自動転送

たとえば、Google Workspace や Microsoft 365 の `support@company.example` が、`ecookbook@redmine.example.com` に転送するものです。

- **プロジェクト:** エンベロープの宛先 (`receipt.recipients`。「the envelope RCPT TO addresses」) から決めます。プロジェクトのアドレスが入っています。`To` と `Cc` のヘッダー (`mail.destination`。「from the MIME headers」) には `support@company.example` が入っているので、使いません。
- **作成者:** DMARC に合格したメッセージは、ほかのメールと同じく、差出人 (`From`) です。Redmine のルール (プロジェクトの「未登録の送信者」の設定と、送信者の権限) に従います。登録した転送元から届いたことだけで取得したメッセージ (DMARC に失敗したもの) の `From` は、何も認証していないので、作成者は「転送メールの作成者」(下記) に従います。
- **DMARC:** 転送すると、DMARC に失敗することがよくあります。転送元は自分のサーバーから送るので、SPF が元の差出人のドメインと一致せず、メッセージを変える転送元は DKIM の署名を壊すからです (メッセージを変えずに転送すれば、たいてい署名が残り、DMARC に合格します)。DMARC に失敗したメールは、プロジェクトの「転送元」(アドレスまたはドメイン) で判断します。SES の SPF の判定 (`receipt.spfVerdict`) が `PASS` で、エンベロープの送信者 (`mail.source`。「the envelope MAIL FROM address」) が登録した転送元のもの (そのドメイン、またはそのアドレス。`+` のタグ付きも含む) のときだけ取得します。それ以外は取得しません (「未取得 (DMARC 失敗)」。エンベロープの送信者が転送元のもので SPF に失敗したときは「未取得 (転送元の SPF 失敗)」)。「DMARC に失敗したメールも取得」は、これまでどおり使えます。
- **エンベロープの送信者を使う理由:** エンベロープの送信者を Sender Rewriting Scheme (SRS) で書き換える転送元は、MAIL FROM に自分のアドレスを入れ、SPF はそのドメインで確認されます。Microsoft 365 は、メールボックスの転送、受信トレイのルールのリダイレクト、メールフロールールのリダイレクトで、`<転送するメールボックスの @ の前>+SRS=…@<転送するメールボックスのドメイン>` (または `bounces+SRS=…@<既定の承認済みドメイン>`、`bouncesEtr+SRS=…@<既定の承認済みドメイン>`) に書き換えます ([Sender Rewriting Scheme (SRS) in Microsoft 365](https://learn.microsoft.com/en-us/exchange/reference/sender-rewriting-scheme))。どれにも当てはまるように、転送元のドメイン (`company.example`) を登録します。
- **登録した転送元が信頼するもの:** ドメインを登録すると、そのエンベロープのドメインで送り、SPF に合格できる人、つまりそのドメインのメールサーバーから送れる人すべてを信頼します。ドメインを登録するのは、自分の組織のドメインのときだけにします。共有のプロバイダー (`gmail.com`、`outlook.com` など) は、ドメインではなく、転送するアドレスで登録します。転送元を変えられるのはシステム管理者だけです。

**Microsoft 365:** Exchange 管理センターで **[受信者]** > **[メールボックス]** を開き、メールボックスを選び、**[メールの転送]** の **[メール転送の管理]** を選びます。**[このメールボックスに送信されたすべてのメールを転送する]** をオンにし、**[外部のメール アドレスに転送する]** を選んでプロジェクトのアドレスを入れ、保存します。**[転送先アドレスとメールボックスの両方にメッセージを配信する]** を選ぶと、コピーが残ります ([Configure email forwarding for a mailbox in Exchange Online](https://learn.microsoft.com/en-us/exchange/recipients-in-exchange-online/manage-user-mailboxes/configure-email-forwarding))。外部のアドレスへの自動転送は、スパム対策の送信ポリシーで許可する必要があります ([Control automatic external email forwarding in Microsoft 365](https://learn.microsoft.com/en-us/defender-office-365/outbound-spam-policies-external-email-forwarding))。転送するメールボックスのドメイン (既定の承認済みドメインが違うときは、それも) を転送元に登録します。画面の日本語の表記は、英語の資料からの訳で、画面では確認していません。

**Google Workspace:** Google 管理コンソールで **[アプリ]** > **[Google Workspace]** > **[Gmail]** > **[ルーティング]** を開き、**[受信者アドレス マップを使用したメール転送]** で、アドレス (`support@company.example`) をプロジェクトのアドレスに対応させるルールを追加します ([Redirect or forward Gmail messages to another user](https://knowledge.workspace.google.com/admin/gmail/advanced/redirect-or-forward-gmail-messages-to-another-user))。転送したメッセージのエンベロープの送信者がどうなるかは、Google の資料に書かれていません。転送元に頼る前に、DMARC に失敗するテストのメールを送り、「メール受信」のタブで結果を確認してください ([setup.md](setup.md#to-verify) の「未確認の事項」)。画面の日本語の表記は、英語の資料からの訳で、画面では確認していません。

<a id="forwarding-by-members"></a>

### メンバーによる転送

メンバーが、顧客のメールを、メールソフトからプロジェクトのアドレスに転送するものです。プロジェクトの「メンバーが転送したメールを元のメールとして取得」をオンにすると (デフォルトはオフ)、元のメールからチケットを作ります。

- **対象:** 送信者が、そのアドレスを持つ有効な Redmine のユーザーで、そのメッセージが DMARC に合格していて (そのアドレスが本人のものだとわかる)、プロジェクトにチケットを追加できるときだけです。それ以外は、送信者からのふつうのメッセージとして取り込みます。
- **元のメールの見つけ方:** 件名の前に `Fwd:`、`FW:`、`転送:` があるときだけです (`.eml` が添付されていても、この件名でなければ転送ではありません)。`message/rfc822` で添付された転送メッセージ (添付ファイルとして転送)、または本文の転送ブロックです。Gmail の `---------- Forwarded message ---------` (`---------- 転送されたメッセージ ---------`) の行のあとの、元のメールの `From:`、`Date:`、`Subject:`、`To:`、または Outlook の `From:`、`Sent:`、`To:`、`Subject:` (`差出人:`、`送信日時:`、`宛先:`、`件名:`) の行です。いちばん外側の転送だけを使い、その中の転送は本文に残ります。
- **チケット:** 元のメールの件名、本文、添付ファイル (本文の転送では、転送メールの添付ファイル) から作ります。作成者は「転送メールの作成者」(下記) に従います。添付された元のメールの `To` と `Cc` は、Redmine が追加するとおりにウォッチャーになりますが、権限 (「ウォッチャーの追加」) は作成者ではなくメンバーのもので確認します。メンバーがチケットを見られるときは、メンバーをウォッチャーに追加します。メンバーが注記を追加できる (「コメントの追加」の権限がある) ときは、メンバーの注記を、Redmine のデフォルトの言語で残します (「`<アドレス>` からのメールを転送しました。」)。注記には、メンバー自身の文と、転送メールそのものの添付ファイル (添付された元のメールのほか) も残します。Redmine がコミットの注記を書くのと同じ方法 (`init_journal` のあと `save`) で、カスタムフィールドを設定しなくても、誰がいつ転送したかが履歴でわかります。
- **信頼できない内容:** 元のメールは、メンバーが責任を持つ転送メールの中身です。元の差出人には、Redmine のルールがそのまま適用されます。元のメールの `In-Reply-To` と `References` は外し、件名がチケットやメッセージを指す元のメール (`[… #123]`) は、メンバー自身のメッセージとして取り込みます。転送でほかのチケットに注記が付くことはありません。40 MB の上限は、元のメールにも適用します。
- **なくさない:** 元のメールが見つからない、読めない、Redmine が受け付けない (たとえば、権限のない作成者) 転送メールは、メンバー自身のメッセージとして取り込みます。

<a id="author-of-forwarded-email"></a>

### 転送メールの作成者

プロジェクトの「転送メールの作成者」で、転送メールから作るチケットの作成者を決めます。メンバーの転送と、登録した転送元から届いたメッセージの両方に適用します。元の差出人の名前は認証されていない (メンバーが責任を持つか、転送元の SPF に合格しただけ) ので、「ユーザーを作成」と同じく、選べるのはシステム管理者だけです。

| 設定 | 元の差出人を作成者にするとき | それ以外のとき |
| --- | --- | --- |
| プロジェクト外の送信者 (デフォルト) | 有効な Redmine のユーザーで、システム管理者でも、プロジェクトのメンバーでもない | 転送したメンバー。自動転送では、プロジェクトが未登録の送信者から取得するなら匿名ユーザー |
| 登録済みのユーザー | 有効な Redmine のユーザー | 同上 |
| 元の差出人にしない | しない | 同上 |

- **Redmine が知らない送信者:** 上の 2 つの設定では、プロジェクトが未登録の送信者から取得する (「匿名ユーザーとして取得」か「ユーザーを作成」) なら、匿名ユーザーのチケットにします。そうでなければメンバーのものです。元の差出人からユーザーを作ることはありません。「ユーザーを作成」は転送メールには適用しません。
- **作成者がいないとき:** 登録した転送元から届いたメッセージで、作成者にできる人がいないもの (たとえば、差出人がプロジェクトのメンバーで、プロジェクトが未登録の送信者から取得しない) は取得しません (「未取得 (転送メールの作成者なし)」)。
- **記録:** 元の差出人は、受信履歴 (差出人) に残ります。メンバーの転送では、メンバーの注記にも残ります。
- **実装:** 作成者は `RedmineAws::SES::Admission#author` で決めます。Redmine の `MailHandler` のサブクラス `RedmineAws::SES::ForwardedMailHandler` が、それを差出人の代わりにし (private の `dispatch` をオーバーライド)、ウォッチャーの権限をメンバーで確認します (private の `add_watchers` をオーバーライド)。どちらも `super` を呼びます。

<a id="settings-for-receiving-replies"></a>

## 返信を受信するための設定

| 設定 | 値 | 理由 |
| --- | --- | --- |
| Redmine の管理画面の「送信元メールアドレス」 | デフォルトアドレス (例: `noreply@redmine.example.com`) | プラグインは、ここから Redmine のドメインも知る |
| 「メール本文から一致する行以降を切り捨てる」 | 引用の前の行 (「--- この行より上に返信を書いてください ---」など) | 返信の引用を注記に入れない |
